THE GHOST IN THE SUBNET: A MIDNIGHT TRACE
=======================================

PHASE 1: THE ALERT
-------------------
The PagerDuty siren didn't just wake me; it sheared through three hours of sleep like a bandsaw through plywood.

02:14:03 UTC — ALERT [CRITICAL]: prod-east-api-gateway latency > 8500ms (threshold: 200ms). Packet loss: 14.2%.

I blinked into the glare of my laptop monitor, my terminal screen blooming open with a sea of red status dashboards. Out of our 120 microservices, 40 were throwing circuit-breaker exceptions. Customers across Europe and North America were seeing high-friction connection timeouts (ERR_CONNECTION_RESET).

"Is it BGP hijacking?" pulled up on Slack. It was Marcus, our Lead Site Reliability Engineer, already typing furiously from his kitchen table in Berlin.

"Doubt it," I typed back, running my fingers across the keys, still thick with sleep. "Upstream Transit Providers look clean on ThousandEyes. The edge load balancers are passing health checks, but the moment traffic hits the internal mesh layer, it’s dropping into a black hole."

"Which subnets?"

"All of them. Or none of them. It's flapping."

I logged into our central edge aggregator, gw-edge-01.internal.net, elevated to root, and triggered a packet capture across our primary internal boundary interface (eth0).

$ sudo tcpdump -i eth0 -nn -c 100000 -w /tmp/midnight_dump.pcap "tcp[tcpflags] & (tcp-syn|tcp-rst) != 0"

In under twelve seconds, the buffer filled. A hundred thousand flags snapped into the capture file. I pulled down the raw text stream using a quick script to inspect the source and destination IP pairs.

What spilled across my terminal wasn't a standard denial-of-service attack or a broken routing table. It was an asynchronous storm.

PHASE 5: THE ROOT CAUSE UNFOLDS
-------------------------------
Everything fell into place.

Two hours earlier, at 00:00 UTC, an automated deployment pipeline had pushed a security update to our Envoy sidecar proxies: a custom WebAssembly (Wasm) filter designed to perform real-time Certificate Revocation List (CRL) checking for inbound client TLS certificates.

The filter had been hardcoded with a fallback IP array pointing to an old internal revocation endpoint: 172.16.4.12 through 172.16.4.255.

Here is how the failure cascaded through the infrastructure:

+-----------------------------------------------------------------------------------------------------+
| CASCADE FAILURE SEQUENCE                                                                            |
+-----------------------------------------------------------------------------------------------------+
|                                                                                                     |
|  1. Ingress Proxy (192.168.10.45) forwards validated client request to Auth Service (10.240.12.102).|
|                                                                                                     |
|  2. Envoy Sidecar on 10.240.12.102 intercepts request and triggers WASM CRL Filter.                 |
|                                                                                                     |
|  3. WASM Filter attempts synchronous HTTP connection to legacy CRL server at 172.16.4.12:443.       |
|                                                                                                     |
|  4. Packet routed via default management bridge (10.240.99.1) -> Targets dead subnet.               |
|                                                                                                     |
|  5. Connection Refused (RST) / Timeout occurs. WASM Filter loops through fallback IPs:             |
|     172.16.4.12 -> 172.16.4.13 -> 172.16.4.14 ... up to 172.16.4.255                                 |
|                                                                                                     |
|  6. Worker threads exhausted waiting for synchronous network I/O timeouts.                          |
|                                                                                                     |
|  7. Envoy drops incoming connection, sending TCP RST back to Ingress Proxy (192.168.10.45).        |
|                                                                                                     |
|  8. Ingress Proxy retries down the line: 10.240.12.103, 10.240.12.104, 10.240.12.105...             |
|                                                                                                     |
|  9. All sidecars hit identical timeouts -> Global API Meltdown.                                     |
|                                                                                                     |
+-----------------------------------------------------------------------------------------------------+

Because the CRL check was configured as a synchronous block, Envoy withheld the ACK/Payload processing for incoming requests from 192.168.10.45 while attempting to query the non-existent 172.16.4.x range. Once the filter exhausted its socket retries, it panicked and reset the client connection with a TCP RST flag.

The API proxies (192.168.10.45, .46, .47), receiving unexpected resets, immediately retried their payloads against other backend Auth replicas (10.240.12.103, 10.240.12.104, 10.240.12.105). Within minutes, thousands of retry requests flooded every node in the microservice mesh, creating a thundering herd that locked up all worker threads across the entire internal subnet.


PHASE 6: RESOLUTION AND MITIGATION
----------------------------------
"We need to bypass that WASM filter immediately," Marcus said. "I’m triggering a rollback of the Envoy config deployment."

"Wait," I interrupted, looking at the deployment locks. "A full pipeline rollback will take 15 minutes to clear canary stages. We can fix this at the network layer in 10 seconds."

I wrote a zero-downtime hotfix using iptables rules directly on the transit routers to redirect traffic meant for the dead 172.16.4.0/24 subnet straight to a local dummy interface returning instant HTTP 200 responses, while we pushed a hot-patch to drop the static route.

# 1. Immediately null-route the dead range to stop outbound ARP/SYN storms
sudo ip route add blackhole 172.16.4.0/24

# 2. Force local Envoy instances to abort the blocking CRL lookup instantly
sudo iptables -A OUTPUT -d 172.16.4.0/24 -p tcp --dport 443 -j REJECT --with-tcp-reset

The moment those two commands propagated across the cluster via Ansible:

1. Outbound SYN packets to 172.16.4.x dropped to zero.
2. Envoy WASM filters received immediate local TCP RSTs instead of hanging on socket timeouts.
3. The fallback mechanism in the WASM code failed-open instantly, allowing normal HTTP payload processing to resume.

I re-ran tcpdump to verify the packet flow:

KEY TECHNICAL TAKEAWAYS
-----------------------
* Synchronous Network I/O in Proxies is Dangerous: Never perform blocking network requests inside a hot proxy filter path without strict timeouts (e.g., <5ms).
* Dead Subnet Routing: Deprecated subnets (172.16.4.0/24) should be explicitly blackholed at the router level rather than left unrouted, preventing ARP sweeps or SYN retries from consuming system sockets.
* Fail-Open Architecture: Security features (like CRL or OCSP checks) must default to failing open when upstream validation servers are unreachable to prevent total system outages.
